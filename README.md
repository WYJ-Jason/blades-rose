# 《血与刃的白蔷薇》辅助工具

**在线打开：[https://blades-rose.onrender.com/](https://blades-rose.onrender.com/)**

线下聚会用的多人 Web 工具。每人一台手机／平板／电脑，扫码或输入 PIN 进同一房间。系统代替实体身份牌、手牌、白水晶、金币和主版图，负责私密发牌、流程、限制、结算和胜负。

- 5～10 人，一设备一席位，不注册账号。
- 房主建房后得到短 PIN 和二维码；界面统一用「座位号＋昵称」。
- 不内置聊天或语音，讨论仍在线下。
- 服务端是唯一真实状态；客户端只收到自己有权看的信息。
- 无需任何实体组件即可打完一局。

## 启动

已部署站点：**[https://blades-rose.onrender.com/](https://blades-rose.onrender.com/)**（推送到 `main` 后自动更新）。

需要 **Node.js 22+**。

```bash
npm install
npm run build
npm start
```

| 用途 | 命令 | 地址 |
| --- | --- | --- |
| 聚会（生产） | `npm run build` 然后 `npm start` | 网页和对局都在 `http://localhost:3000` |
| 同一 Wi‑Fi | 同上 | 终端会打印 `http://192.168.x.x:3000` |
| 开发 | `npm run dev` | 网页 `http://localhost:5173`，实时服务仍是 `:3000` |
| 规则测试 | `npm test` | — |

环境变量：`PORT`（默认 `3000`）、`DATA_DIR`（默认项目下 `data`）。

### 同一 Wi‑Fi

局域网 IP 只在同一路由器下可用。手机必须连同一 Wi‑Fi，不能用流量。房主打开本机或局域网地址即可，二维码默认用局域网地址。

### 跨网络

平时直接打开已部署站点 [https://blades-rose.onrender.com/](https://blades-rose.onrender.com/)。邀请二维码和链接会使用这个地址。

若在本机跑服务、又要让外网加入，可用免费 Cloudflare 临时隧道（地址每次随机，不能自定义域名）。本机 `npm start` 之后另开终端：

```bash
npm run tunnel
```

刷新房主页面，二维码会换成隧道地址。**隧道窗口必须一直开着**；关掉即失效，下次再开会拿到新地址。

## 规则概要

两阵营：

- **白蔷薇**：保护白蔷薇，并让足够数量的花苞献祭成功。
- **血刃**：杀死白蔷薇，或杀死足够数量的花苞。

没有投票放逐。每轮玩家依次决定是否暗出一张牌，服务端收集后混洗公开。白蔷薇要判断这一轮会不会出刀，血刃要判断白蔷薇和花苞何时出现。

每人通常三张手牌：固定信者、固定幽魂、一张随机角色牌（决定身份和阵营）。**双刃例外**：幽魂被换成第二张双刃，手牌为「双刃×2＋信者」，被替换的幽魂进入中央备用区，供 7 号水晶使用。角色牌打出后阵营不变。

| 阵营 | 角色 | 要点 |
| --- | --- | --- |
| 白蔷薇 | 白蔷薇 | 与任意血刃同一轮公开则血刃立即获胜 |
| 白蔷薇 | 司教、信者 | 结算时算花苞 |
| 血刃 | 双刃 | 两张双刃，两次出刀 |
| 血刃 | 巨刃、暗刃 | 各一张血刃；暗刃开局无相认 |
| — | 幽魂 | 公开后移除；不献祭、不被血刃杀死，用于伪装 |

## 房间与座位

1. 房主创建房间，得到短 PIN 和二维码。
2. 其他人扫码或输入 PIN，填昵称占一个席位。昵称可以重复，靠座位号区分。
3. 房主按线下实际座位拖动排序；系统生成连续座位号。
4. 满 5 人后，页面按人数展示身份配置、献祭／死亡门槛和最大回合数。
5. 房主锁定座位并开始：服务端随机分配身份、初始手牌和白水晶。

一个有效玩家令牌只绑定一个席位。刷新或短暂断线时，原设备用该令牌恢复席位和私密信息。

座位号同时决定顺时针出牌顺序和左右邻座。3、4、8 号水晶都按锁定后的座位确定目标；首尾座位彼此相邻。对局中不能调座，下一局准备阶段房主可以重排。

## 相认

数字版不做集体闭眼／睁眼。发牌完成后：

- 白蔷薇、司教、双刃、巨刃收到相认名单：只含其他可相认玩家的「座位号＋昵称」，不含角色和手牌。
- 信者、暗刃开局没有相认名单。
- 双刃直接拿「双刃×2＋信者」，不执行实体版换牌。
- 9 号水晶发动后，暗刃额外私密看到白蔷薇和司教的座位号与昵称。

## 金币

发牌和相认展示后，**房主选择首位金币持有者**（可以是自己）。

- 「初始化金币」**不消耗**房主水晶。
- 被选中的人公开并发动自己的水晶。
- 若选了别人，房主水晶仍未使用，之后仍可被选为金币持有者。
- 若选自己，房主作为首位正常使用自己的水晶。

之后每轮结束，当前金币持有者从**水晶尚未使用**的玩家中选下一位。

## 每轮流程

### 1. 发动水晶

金币持有者先公开水晶，并在所有人选牌之前发动。系统展示完整注解、过滤合法目标、引导选择或私密查看，并设置强制／禁止出牌、顺序调整或延迟效果；客户端不能提交违反限制的操作。

10 号在选牌前发动，但替换步骤要等所有人完成**首次**选牌后再执行。

### 2. 依次选牌

默认从金币持有者起按座位行动；6 号水晶使其改为最后行动。

轮到自己时：从未使用手牌暗出一张，或跳过。水晶可能强制出牌、禁止出牌，或只能打出指定牌。

**强制出牌**只表示该玩家轮到自己时必须选一张牌，不会立刻出牌，也不改变行动顺序。除 6 号外，所有人仍按本轮规则顺序操作。

公共页可以看到谁已决定、选择了「出」还是「过」，看不到暗牌内容。

### 3. 收集并公开

所有人选完后，服务端收集暗牌、随机打乱、统一公开。

- **2 号**：不混洗，公开时显示每张牌来自谁。
- **10 号**：全部首次选择后，先处理可能的暗牌替换，再公开。

### 4. 结算

无血刃：幽魂移出；白蔷薇进圣所；司教和信者进献祭区。

有血刃、无白蔷薇：幽魂移出；本轮所有司教和信者进死亡区。多把血刃杀伤相同，不重复计算同一张花苞。

白蔷薇与任意血刃同时出现：白蔷薇被杀，血刃立即获胜。

### 5. 检查胜负并传金币

每轮结算后自动检查。若无人获胜，当前金币持有者从未使用水晶的玩家中选下一位，进入下一轮。

## 十二种水晶

随时可看自己的编号、名称、完整注解、合法目标和使用状态。另有「图鉴」展示全部 12 种能力，**不显示**别人实际持有哪枚。

### 1. 指定某人必须出牌

选择一名仍有手牌的玩家。轮到该玩家时必须出牌。不能选已经没有手牌的人。不改变行动顺序。

### 2. 本回合不混洗

所有人选完后，本轮暗牌不混洗，按来源公开，所有人知道每张牌由谁打出。

### 3. 右边随机抽一张手牌

从右侧玩家手牌中随机锁定一张，不向水晶持有者公开牌面。该玩家本轮必须打出被锁定的牌，不能跳过。右侧没有手牌时不发动。

### 4. 左边随机抽一张手牌

与 3 号相同，目标改为左侧玩家。

### 5. 指定两人出牌

依次指定仍有手牌的 A、B，两人按 **A → B** 的顺序选择是否出牌。A、B 仍在各自原定轮次操作，不会提前出牌。不能选已经没有手牌的人。若 A 不出但 B 出了，则本轮结束前 A 必须补出一张牌。

### 6. 我最后决定是否出牌

金币持有者由本轮第一位改为最后一位决定是否出牌。

### 7. 指定某人拿一张幽魂

选择自己以外的一名玩家，把中央备用区的幽魂加入其手牌。

### 8. 左右两家有牌必须出牌

左右相邻玩家只要还有手牌，本轮就必须在自己的正常轮次出牌。

### 9. 暗刃看白蔷薇和司教

不模拟闭眼。仅向暗刃私密显示白蔷薇与司教的座位号和昵称，其他人收不到。

### 10. 最后决定是否替换出牌

所有人完成首次选牌后，可令一名**已出牌且仍有手牌**的玩家（**可以是自己**）从剩余手牌中选一张替换暗牌。

- 水晶持有者看不到目标原本打出的暗牌。
- 原本打出的牌回到目标手中。

### 11. 抽某人一张牌偷看

选择一名有手牌的玩家，服务端随机抽一张仅给水晶持有者看，随后归还。系统不代为公开；持有者可在线下说出、隐瞒或说谎。

### 12. 指定某人必须出牌

与 1 号相同：选择一名仍有手牌的玩家，轮到时必须出牌，行动顺序不变。

## 胜负

白蔷薇可先安全进圣所再补献祭，也可先献祭够再找机会打出白蔷薇。

**白蔷薇胜（任一）：**

1. 白蔷薇已安全进入圣所，且献祭区达到当前人数要求的花苞数量。
2. 全部水晶用完后，所有玩家手牌中都没有未打出的花苞（司教、信者），且白蔷薇也不再留在手牌中。

**血刃胜（任一）：**

1. 白蔷薇和任意血刃在同一轮出现。
2. 死亡区达到当前人数要求的花苞数量。
3. 全部水晶用完后，任意玩家手牌中仍有未打出的花苞（司教或信者）。
4. 全部水晶用完后，白蔷薇仍留在手牌中。

最终回合检查**所有**玩家手牌中的花苞，包括血刃未打出的信者。

## 提前结束与下一局

对局中任意玩家可发起提前结束投票，全员弹窗同意或继续。同意人数必须**严格超过半数**（5 人 3 票，6 人 4 票，7 人 4 票，8 人 5 票，9 人 5 票，10 人 6 票）。达标后立即终止本局，不判定阵营获胜。房主可在对局中直接解散房间。

正常结束或提前结束后：保留 PIN、昵称、席位和房主；清空角色、手牌、水晶、相认、投票和本局状态；全员回到下一局准备页；按当时人数重新展示配置；房主确认后重新随机发牌开新局。

## 公开与私密信息

**所有人可见：** 阶段和流程说明；当前行动者与金币持有者；昵称、在线、座位号（公共和私密标签都是「座位号＋昵称」）；水晶未使用／已使用；已公开水晶的编号和能力；主版图（圣所、献祭、死亡）；胜利门槛；回合与结算记录；提前结束票数。

**仅自己可见：** 角色和阵营；相认名单；完整手牌及已使用牌的去向；水晶编号、名称、注解和使用状态；当前允许的私密操作。开始游戏后身份会先弹窗确认；对局页私密信息和手牌默认收起，轮到出牌或替换暗牌时再展开手牌。

## 技术

### 栈

| 层 | 技术 |
| --- | --- |
| 前端 | React 19、TypeScript、Vite、移动端优先 PWA、Socket.IO Client |
| 服务端 | Node.js 22、Fastify、Socket.IO、服务端权威状态 |
| 数据 | Node 内置 SQLite，默认 `data/rooms.sqlite`，可用 `DATA_DIR` 修改 |

### 仓库结构

单包，不是 `apps/` 多包工作区：

| 路径 | 作用 |
| --- | --- |
| `src/App.tsx` | 大厅、房间、对局、手牌、水晶、结算弹窗 |
| `src/styles.css` | 移动端优先样式 |
| `src/game.ts` | 房间状态机、发牌、水晶、结算、胜负 |
| `src/shared.ts` | 前后端共享协议、角色、水晶定义 |
| `src/server.ts` | HTTP、Socket 事件、快照、PIN／令牌、静态 `dist` |
| `scripts/build.mjs` | 生产前端构建 |
| `scripts/tunnel.mjs` | Cloudflare 临时隧道，把公网地址写入 `data/public-url.txt` |
| `tests/game.test.ts` | 规则单元测试 |
| `Dockerfile` | 单容器：静态页 + API + WebSocket |

### 部署

单个 Docker 容器同时提供前端静态资源、API 和 WebSocket。目标环境需要支持长连接。把 `DATA_DIR` 对应目录挂到持久磁盘。玩家只需打开网址，不用装应用。

```dockerfile
# 镜像内：PORT=3000，DATA_DIR=/app/data，CMD npm start
```

### 信息隔离

- 服务端是发牌、随机数、规则执行和胜负的唯一权威。
- 公共状态与玩家私密状态使用不同数据结构；房间广播不含全量身份、手牌、相认名单或未公开水晶。
- 玩家只能提交当前阶段允许的命令。命令校验房间、令牌、行动顺序、卡牌所有权和合法目标。
- 断线重连恢复原席位，不能以新身份再进正在进行的房间窥牌。
- 日志只记动作类型和状态版本，不记未公开牌面。

## 测试与验收

**测试重点**

- 5～10 人身份数量和胜利门槛。
- 双刃初始手牌与中央备用幽魂。
- 相认名单只向合法角色发送。
- 房主初始金币选择不错误消耗房主水晶。
- 所有水晶发动均先于玩家首次选牌。
- 强制出牌只改变该玩家在自己轮次中的可选操作，不得改变正常行动顺序。
- 2 号不混洗、5 号 A→B 与补牌、6 号顺序调整、9 号暗刃视野、10 号可替换自己。
- 1、5、8、12 号的强制出牌冲突和无手牌边界。
- 3、4、11 号使用服务端随机数且不泄露额外信息。
- 座位号连续且唯一，房主排序后正确决定顺时针顺序及首尾相邻。
- 白蔷薇遇刺、献祭达标、死亡达标、最终回合（含任意手牌残留花苞）。
- 超过半数提前结束，以及保留房间进入下一局。
- 客户端无法收到其他玩家的身份、手牌或未公开水晶。

**验收标准**

- 5～10 名玩家可以仅凭各自联网设备完成一整局。
- 房间支持二维码和 PIN 两种加入方式。
- 所有玩家均以「座位号＋昵称」显示，座位顺序正确驱动出牌和邻座能力。
- 系统能根据人数自动配置并展示规则。
- 所有角色、手牌、水晶和相认信息正确隔离。
- 12 种水晶均能按规则发动并限制选牌。
- 主版图、手牌历史、水晶进度和流程实时同步。
- 能自动结算并正确判断胜负。
- 多数玩家可以提前结束，并在原房间开始下一局。
- 刷新或短暂断线不会丢失席位或私密状态。
